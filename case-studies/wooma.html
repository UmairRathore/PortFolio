Key Engineering Decision: Reliability Over Maximum Concurrency

One production worker and one active migration intentionally limited pressure on the live source and destination databases. Predictable load and recoverability mattered more than maximum throughput. Persistent state enabled interrupted jobs and worker restarts to resume safely. Logically independent workflows did not mean simultaneous physical execution.

01 / OVERVIEW AND OWNERSHIP

One pipeline. Two operational products.

I was the sole engineer responsible for the migration pipeline architecture, implementation, production deployment, and execution. I developed both the Laravel/PHP migration pipeline and the Python asset extractor used during preservation. The legacy reporting platform and Wooma were already operational SaaS platforms. My ownership was the migration system connecting them, not the development of either complete product.

Laravel/PHP migration system

Laravel handled migration orchestration, tenant-aware processing, persistent state, Redis queues, locks, report import, and administrative approvals. I personally deployed the Laravel migration pipeline to production.

Python asset extractor

I developed a Python-based extractor for the asset-preservation phase. Extracted assets were processed through the existing preservation pipeline. Python's role was asset extraction within that workflow.

02 / THE PROBLEM

Move the history without losing control.

Scale inside live systems

Some tenants held around 8K to 10K reports. The largest held approximately 104K. Both platforms remained live, so tenant isolation and database safety were essential throughout the migration.

Documents were only part of the move

PDFs referenced external resources that also needed preservation. Interrupted execution had to recover without restarting a whole tenant, and customer access needed a controlled release.

03 / ARCHITECTURE

A persistent control plane, tenant-aware delivery.

Administrators controlled migration initiation. Laravel queues and Redis-based orchestration coordinated discovery, downloads, parsing, import, and asset preservation. A central control database maintained tenant mapping, processing metadata, state, errors, and progress. Business data was imported into the appropriate destination tenant database.

Redis distributed locks coordinated processing, while database locks and transactions protected database changes. S3 and Hetzner storage were accessed through storage adapters, keeping storage access separate from migration orchestration.

04 / PROCESSING LIFECYCLE

Small jobs. Durable progress.

  1. Authentication and tenant mappingAfter administrator-controlled initiation, authenticate against the source tenant and resolve the correct destination tenant connection.
  2. DiscoveryEnumerate reports through paginated discovery and retain processing records in the control database.
  3. PDF downloadRetrieve and preserve PDFs through individual download jobs with recorded progress and failures.
  4. ParsingExtract structured data from the preserved PDF for the destination report model.
  5. Data importImport into the mapped tenant database using tenant-scoped idempotency, transactions, and locks.
  6. Asset preservationUse individual asset records and retryable preservation jobs to track external resources independently from report import, including errors and operational progress.
  7. Approval and cutoverRelease report visibility after validated import, then switch asset references after the required preservation and import work is complete.
Batch size is not concurrency. Discovery and download jobs were organized in controlled batches of 20 jobs. Individual PDF downloads and asset preservation used granular jobs. A batch of 20 did not mean 20 simultaneous workers.
05 / RELIABILITY ENGINEERING

Recovery was part of the architecture.

Durable state and safe retries

Persistent migration records retained processing state, errors, and progress. Tenant-scoped idempotency kept repeated work tied to the correct tenant. Retry-safe jobs, Redis locks, database locks, and database transactions protected against duplicate processing and unsafe database changes.

Completion beyond the queue

Report import and asset preservation had independent completion tracking. Reconciliation used persisted state and recorded failures rather than assuming that an empty queue meant a completed migration. Interrupted runs could resume without a whole-tenant restart.

Database and storage have different boundaries. Database transactions do not automatically roll back external object storage operations. Stored objects and database records must be reconciled as separate effects during retries and recovery.
06 / TWO-STAGE ADMINISTRATIVE CUTOVER

Release data first. Move asset ownership second.

Approval gate 1

Make validated report data visible

After validated import, an administrator could approve customer access to the imported reports. At this point, assets could still reference resources hosted by the legacy reporting platform.

Approval gate 2

Switch to preserved assets

After successful asset preservation, a separate approval allowed references to switch to assets controlled by Wooma. This second approval depended on completion of the required preservation and import work. Separating report visibility from asset independence allowed validated data to become accessible before the final asset switch, reducing cutover risk.

Source-retirement safety. A 30-day grace period preceded removal of original source resources, providing a safety window alongside the two administrative approval gates.
07 / PRODUCTION TRADE-OFF

Deliberately serial. Operationally recoverable.

Production used one active migration and a single worker to protect the live source and destination systems. This intentionally traded throughput for controlled load and reliable operation. Multi-tenant routing and logically separate workflows did not imply parallel processing.

08 / OUTCOMES

A successful production migration with controlled release.

  • 15+ UK property-management companies successfully migrated without disrupting their live operations.
  • 250,000+ historical PDF reports imported across all migrated tenants, with both applications remaining operational.
  • Approximately 12.5 million associated assets across the full migration, estimated as 250,000 × an average of 50 per report.
  • The largest tenant contained approximately 104,000 reports, with approximately 5.2 million associated assets estimated as 104,000 × 50.
  • Approximately two weeks to migrate the largest tenant using deliberately constrained worker concurrency. This duration does not describe the aggregate migration.
  • State-based recovery prevented whole-tenant restarts.
  • Staged approvals enabled controlled customer access and the later switch to preserved assets.
09 / TECHNICAL DEEP DIVE

Inside the recovery model.

Explore state, integrity, retries, and approval gates

State machine transitions

The model below summarizes processing responsibilities, not internal enum names. Successful stages advance through persisted progress; a failed stage records an error and returns to eligible processing through retry or resume.

Discovered → PDF preserved → Parsed → Imported → Validated

Asset preservation has a separate completion path. An imported report is not proof that its associated assets have been preserved.

Tenant-scoped deduplication

Idempotency was scoped to the tenant, so repeated processing of a source report could be recognized within the correct migration context. The control database held mapping and progress; tenant-aware connections routed business records into the appropriate destination database.

Queue and worker architecture

Laravel queues and Redis orchestration separated work into recoverable units. Controlled batches contained 20 jobs, while individual downloads and asset-preservation operations remained granular. One active migration and one production worker limited pressure on both operational platforms.

Database integrity and storage-adapter boundaries

Redis distributed locks coordinated processing, while database locks and transactions protected database integrity. These protections did not create a transaction spanning the database and external storage accessed through S3 or Hetzner adapters. Recovery had to account for a stored object and an unfinished database stage separately.

Retries and resume

Persisted state identified completed work and unfinished stages after interruption. Tenant-scoped idempotency and retry-safe jobs allowed work to be revisited without restarting the tenant. Logged failures preserved the context needed to recover the affected processing stage.

Completion and reconciliation

Reconciliation evaluated persisted report and asset progress, including incomplete and failed work. Queue emptiness alone could not establish success. Import completion and asset completion remained distinct prerequisites for the appropriate release decision.

Two approval gates, two decisions

The first approval released validated imported report data. The second allowed references to move to Wooma-controlled assets once the required import and preservation work was complete. Keeping these gates separate prevented data visibility from being confused with asset readiness.
