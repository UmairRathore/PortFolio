Translation & Localization SaaS API

Production AI-powered JSON localization with metered usage and resilient inference.

A Laravel SaaS application connected to a separate Python/FastAPI service running local NLLB translation inference. The engineering challenge was to preserve localization structure while coordinating usage quotas, asynchronous work, and dependency failures.

Key Engineering Decision: Separating SaaS/Business Orchestration from AI Inference

Laravel handled multi-tenant access, users, Stripe usage-based billing, word-based quotas, and asynchronous orchestration. Python/FastAPI served the locally hosted NLLB model using CPU inference. Separating these responsibilities kept model execution outside business logic and the incoming HTTP request. The trade-off was a service boundary requiring timeouts, retry-safe state, and circuit-breaker protection.

01 / PRODUCT AND CLIENT CONTEXT

Translate the content. Preserve the structure.

The Malaysian Upwork client needed a SaaS platform for translating JSON localization files into other languages. Users submitted structured localization content and received localized JSON output, with measured word usage counted against their available allowance.

The product combined a Laravel web platform and administration experience with a backend API. A separate local inference service ran NLLB machine translation, avoiding the need to outsource every translation to an external paid LLM API.

02 / WHAT I ENGINEERED

From application architecture to production delivery.

I was responsible for architecture, implementation, integration, testing, containerization, and delivery of the complete solution.

SaaS application and API

Laravel authentication and multi-tenant access, web and admin interfaces, JSON request handling, word metering, atomic quota reservation and rollback, asynchronous jobs, and persistent processing state. PostgreSQL provided application persistence, with Stripe supporting usage-based billing.

Inference and delivery

Python/FastAPI integration for local NLLB inference, dependency failure handling, and circuit-breaker protection. I Dockerized, tested, deployed, and successfully delivered the solution.

03 / SYSTEM ARCHITECTURE

Separate application rules from model execution.

Laravel owned application behavior, usage accounting, and the request lifecycle. Python/FastAPI exposed a separate API boundary for local translation inference. Queue jobs connected those responsibilities without holding the incoming HTTP request open for model execution.

04 / SERVICE SEPARATION

Two runtimes. Clear responsibilities.

Laravel / PHP

  • User-facing web platform, administration, authentication, and API requests.
  • JSON localization handling, measured word usage, and available quota validation.
  • Redis integration, queue jobs, persisted lifecycle state, locking, and idempotency.
  • PostgreSQL application data and Stripe usage-based billing integration.

Python / FastAPI

  • A separate API boundary for translation requests.
  • Locally hosted NLLB translation inference.
  • Model execution isolated from SaaS business logic.
  • A Dockerized inference runtime, called through the application's circuit-breaker boundary.
05 / WORD-BASED QUOTAS AND REDIS LUA

Avoid the race between checking and consuming.

Translation requests had measurable word usage. Multiple requests for the same account could compete for an available allowance, so quota operations needed atomic coordination rather than separate, unprotected reads and writes.

Redis maintained or coordinated quota-related state. Redis Lua implemented atomic quota reservations and rollback, executing quota operations so concurrent requests could not interleave competing deductions within the same operation. Atomic quota reservation and rollback worked alongside idempotency and persisted processing state to guard against repeated consumption.

Atomic within Redis does not mean transactional across the system. Database locks and transactional boundaries coordinated durable application changes. Redis, PostgreSQL, and inference remained distinct boundaries; explicit quota reservation rollback is an application safeguard, not a transaction spanning Redis, PostgreSQL, Stripe, and inference.
06 / ASYNCHRONOUS REQUEST LIFECYCLE

One translation request, recoverable processing stages.

  1. Receive and validateLaravel accepts localization JSON, validates the request, and measures translatable word usage while preserving structural content.
  2. Coordinate quotaValidate the available allowance and use Redis Lua for atomic quota reservation and accounting.
  3. Queue application workRedis-backed queuing lets Laravel process translation workloads asynchronously, with durable request state supporting the lifecycle.
  4. Execute the translation jobA Laravel job calls the Python/FastAPI inference API through the inference client and circuit-breaker boundary.
  5. Run local inferenceThe Python service uses NLLB to translate the input and return translation results to Laravel.
  6. Persist and retrieveThe application persists translated JSON results and request state for retrieval. Failures are handled through processing state, error handling, retries, and idempotency safeguards.

This sequence shows request-level processing. It does not imply a separate job for each JSON key or establish the exact point at which quota becomes permanently consumed.

07 / IDEMPOTENCY AND CONCURRENCY

Three safeguards for three different problems.

Redis Lua atomicity

Coordinates quota operations when concurrent requests compete for an account's allowance.

Idempotency and persisted state

Guard against duplicate processing and repeated consumption when work is retried.

Database locks and transactions

Coordinate durable application changes and protect persisted request and account state.

A retry is not a new purchase of the same work. Quota accounting and request processing must recognize repeated attempts. Redis atomicity alone does not provide job idempotency, and a database transaction does not undo external inference execution.
08 / LOCAL NLLB AND CIRCUIT BREAKER

Keep an unhealthy dependency from dominating the application.

The Python/FastAPI service ran local NLLB machine translation. My work integrated and operated inference as part of the product; it did not involve training or fine-tuning the model.

The inference client and circuit breaker protected Laravel from repeatedly calling an unhealthy translation dependency. Timeout and error handling, failure isolation, and retry-aware processing kept model execution separate from application business rules during temporary unavailability.

The important boundary was the Laravel application's dependency on the inference API. The locally hosted NLLB model used CPU inference. This deployment choice did not imply GPU inference or model training.

09 / DOCKERIZED PRODUCTION DELIVERY

Delivered as a complete working system.

The complete solution was Dockerized, tested, deployed to production, and successfully delivered to the Malaysian client through Upwork.

Docker provided consistent application and inference environments across the two runtimes. Containerization made the Laravel/PHP application and Python/FastAPI service part of a coherent deliverable while preserving their separate responsibilities.

10 / OUTCOMES AND ENGINEERING TAKEAWAYS

Useful inference needs dependable application engineering.

  • A completed production SaaS for translating structured localization JSON.
  • A local NLLB service integrated with Laravel through a separate inference API.
  • Word-based usage metering with Redis Lua atomic accounting.
  • Asynchronous jobs supported by persisted state, idempotency, and database locks.
  • Dependency protection through circuit-breaker behavior and failure handling.
  • A Dockerized solution tested, deployed, and delivered successfully.

The core lesson was to treat usage accounting, structural correctness, retries, and dependency health as first-class application concerns. Model execution was one part of the production system.

TECHNICAL DEEP DIVE

Reasoning about races, retries, and boundaries.

Explore the request sequence and concurrency safeguards

When two requests compete for quota

Consider two requests reading an account's remaining allowance. With separate unprotected checks and updates, both could proceed using the same apparent balance. Atomic Redis Lua operations prevent that interleaving within the quota operation.

  1. Each request has a measured word usage.
  2. The quota operation evaluates and updates the relevant quota state atomically within Redis.
  3. Persisted request state and idempotency distinguish an existing attempt from newly requested work.
  4. Database locks and transactions coordinate durable application changes.

This explains the safeguards without specifying private scripts, key formats, or deduction timing.

Follow one request through the service boundary

Client → Laravel → Validate + count words → Quota coordination → Queue job → Inference client + breaker → FastAPI → NLLB → Result + persisted state

This is a conceptual sequence rather than internal state enum names. The application tracks progress and failures while the job performs work outside the original HTTP request.

Retries must preserve accounting identity

A failed or interrupted attempt may lead to retry processing. Idempotency and persisted state guard against treating repeated work as a fresh quota consumption or duplicating the same processing. Atomic quota operations and job-level idempotency solve related but different problems.

A timeout is not a cross-service rollback

A timeout or inference error must be handled at the application-to-service boundary. Circuit-breaker behavior reduces repeated calls to an unhealthy dependency. Database transactions do not automatically roll back Redis operations or inference execution, while explicit Redis Lua quota reservation rollback handles the quota boundary. That does not imply a Stripe payment refund or reversal of inference execution.

Keep translation inside the JSON contract

The request contains structured localization content. Validation and input handling identify translatable content, while result handling returns localized JSON without corrupting its structure. The case study does not assume a particular field-level job topology.
